# Collision v2 — Design Doc

**Статус:** Proposed (design only, не реализация)
**Автор:** technical-director
**Дата:** 2026-07-08
**Область:** `web-slice/` (three.js + TS + Colyseus). Godot заморожен.

---

## 0. Продуктовое требование (ранг feel-first, правило владельца)

Коллизия обязана **точно повторять видимый контур** объектов. Игрок должен уметь
ездить впритирку к стенам и камням («на грани»), запутывая противников. Врезание в
невидимый воздух — критический провал. Одновременно: корпус не проходит сквозь
видимую геометрию, включая **корму на переломах склонов**.

Из этого требования вытекают три инварианта, которые дизайн обязан держать:

- **I1 (контур).** Форма коллайдера ≈ силуэт меша в XZ. Никаких «дутых кругов
  вокруг вытянутого тела».
- **I2 (скольжение).** Контакт со стеной гасит только нормальную компоненту
  скорости, тангенциальная сохраняется → можно тереться вдоль стены на скорости.
- **I3 (без провала по Y).** Высота корпуса берётся не из одной точки под центром,
  а из опорного множества под всем следом → корма не тонет, в V-жёлобе корпус
  стоит на двух склонах.

## 1. Текущее состояние и корневые причины трёх провалов

Три независимые подсистемы, каждая со своей моделью формы:

| Подсистема | Где | Форма | Резолюция | Проблема |
|---|---|---|---|---|
| Terrain-стены | `kart.ts` step 8 + `footprintWall.ts` | центр + 4 угла следа, sample heightfield | `null`/rise>MAX_STEP → **обнуление ОСИ** vel | P1: нет скольжения, «липкая» стена, gap ~0.5 клетки |
| Пропсы | `mapLoader.ts` + `kartCollision.ts` | круг из AABB/2·0.8 | `resolveKartPush`, радиус `(0.9+propR)/2` | P2: дутый круг + круг карта 0.9 → «врезаешься в воздух» |
| Kart-vs-kart | `kartCollision.ts` | круг 0.9 | `resolveKartPush` | OK, тюнен — **НЕ трогаем** |
| Высота корпуса | `vertical.ts` + `kart.ts` step 8b | **одна точка** под центром | exp-follow / баллистика | P3: корма тонет, V-жёлоб проваливает корпус |

**P1 root cause.** `footprintHitsWall` возвращает `bool`, а вызывающий делает
`vel.x = 0` / `vel.z = 0` целиком. Прямоугольник следа (полудлина 0.6, полуширина
0.45; углы на расстоянии `√(0.6²+0.45²)=0.75` от центра) крутится вместе с yaw —
угол влезает в соседнюю `null`-клетку, когда тело ещё в ~0.5 клетки от стены, и
глушит всю ось (в т.ч. движение ВДОЛЬ стены). Отсюда «нельзя подъехать впритирку» +
«стена держит».

**P2 root cause.** `resolveKartPush` трактует карт как **точку**, а `minDist =
radius·2 = 0.9 + propR`. Карт-круг 0.9 шире реального тела 0.86 → контакт срабатывает
раньше видимого касания. Плюс круг вокруг несимметричного камня/метеора puffy сам по
себе. `PROP_COLLISION_SHRINK=0.8` — попытка компенсации, которая ломает точность в
обратную сторону.

**P3 root cause.** `stepVertical` получает `groundHeight` = `sample(центр)`. Тело
жёсткое и наклоняется по `attitude.ts` (pitch/roll из 4 проб F/B/L/R), но **высота
привязки** — одна центральная точка. В вогнутом V центр читает дно, углы — склоны;
корпус садится на дно = утопает. На выпуклом переломе корма уходит ниже меша.

**Ключевое наблюдение:** `attitude.ts` УЖЕ семплит 4 точки (F/B/L/R на
пол-колёсной-базы / пол-колеи) для наклона — но только для визуала. Мы переиспользуем
ровно эти пробы для высоты (I3), без нового бюджета семплов.

## 2. Модель форм (I1)

Всё сводим к **2D-выпуклым формам в плоскости XZ** (2.5D аркада). Высота (Y) —
отдельная ось, живёт в heightfield (§4). Общий тип:

```
type Vec2 = { x: number; z: number }

// Выпуклый полигон в XZ, вершины CCW. AABB и OBB — частные случаи (4 вершины).
interface ConvexPoly { verts: Vec2[] }        // мировые координаты
interface Circle     { c: Vec2; r: number }   // только kart-vs-kart
```

### 2.1 Карт

- **Против статики: OBB** (oriented bounding box), полугабариты ≈ видимого тела:
  `halfWidth ≈ 0.42`, `halfLength ≈ 0.83` (тело racer 0.86×1.7, минус skin ~0.02).
  Это то, что даёт «впритирку к плоской стене» и убирает P2-«воздух».
  Центр OBB = `pos`, ось из `yaw` (`forwardOf`/`rightOf`).
  *Почему не capsule:* владелец хочет флеш-парковку к плоской стене — OBB даёт
  ровную грань, капсула оставляет зазор радиуса на углах тела. Риск снага острого
  угла OBB о угол стены — см. §7, митигация skin/капсула-фолбэк.
- **Против карта: круг 0.9** — БЕЗ ИЗМЕНЕНИЙ. Это мягкий тюненый бамп, отдельная
  забота. Две разные формы карта (OBB для статики, круг для карта) — сознательно;
  задокументировать.

### 2.2 Стены `wall_block*`

Важный факт из `assetLoader.ts`: все филеты `wall_block_round` / `wall_block_corner`
скруглят **верхние горизонтальные рёбра** (r=0.12). Вертикальные боковые грани —
полный квадрат 1×1. Значит **в XZ-проекции все три wall_block варианта = полная
клетка 1×1**. Округление невидимо для 2D-коллизии.

→ **wall_block\* = AABB 1×1, выровненный по клетке.** Никакого чтения меша. Опционально
на билде merge соседних wall-клеток в крупные прямоугольники (меньше форм для теста).

### 2.3 Пропсы

| Семейство | Форма | Обоснование |
|---|---|---|
| `STRUCTURAL_PROP_ASSETS` (здания/ракеты/craft) | **OBB** = AABB меша × `def.rot` | боксовые по природе, AABB уже считается в `placeProp` |
| `NATURAL_DECOR_ASSETS` (камни/метеоры/кристаллы) | **XZ convex hull** меша, ≤8 вершин | несимметричные, круг puffy; hull = точный силуэт, «тереться о край» |

Пороги отбора (кто вообще получает коллайдер) остаются как есть:
`MIN_OBSTACLE_DIAMETER=0.6`, `MIN_OBSTACLE_HEIGHT=0.35`, `DECOR_HEIGHT_EXCEPTIONS`.
Меняется только ВЫХОД: не круг, а форма.

**`PROP_COLLISION_SHRINK=0.8` убираем** для hull-семейства: hull и есть контур,
владелец хочет тереться о реальный край. Оставляем микро-skin ~0.02 против джиттера.
Для structural OBB — тоже skin 0.02, без 0.8.

**Критерий выбора формы (сводно):**
1. Клеточный полный бокс (wall_block*) → **AABB** (дёшево, точно).
2. Регулярно-боксовый пропс → **OBB** (AABB×rot).
3. Нерегулярный природный → **convex hull XZ** (fallback OBB если hull вырожден <3 верт).
4. Карт↔статика → **OBB**. Карт↔карт → **круг 0.9** (неизменно).

## 3. Резолюция (I2)

Все статические формы — выпуклые полигоны. Карт — выпуклый полигон (OBB). Единый
примитив: **SAT (Separating Axis Theorem) + MTV (minimum translation vector)**.

### 3.1 Ядро: poly-vs-poly

```
// Возвращает null (нет пересечения) или MTV: нормаль n (единичная, из B в A)
// и глубину penetration.
function satPolyPoly(A: ConvexPoly, B: ConvexPoly): { n: Vec2; depth: number } | null {
  let bestDepth = +Infinity, bestN = null
  for each edge in (A.edges ++ B.edges) {
    axis = normalize(perp(edge))                 // нормаль к ребру
    [aMin, aMax] = projectOntoAxis(A, axis)
    [bMin, bMax] = projectOntoAxis(B, axis)
    overlap = min(aMax, bMax) - max(aMin, bMin)
    if (overlap <= 0) return null                // разделяющая ось → нет контакта
    if (overlap < bestDepth) { bestDepth = overlap; bestN = orientTowardA(axis, A, B) }
  }
  return { n: bestN, depth: bestDepth }
}
```

Для AABB/OBB число осей = 4 (2 уникальных у AABB, 4 у пары OBB). Дёшево.

### 3.2 Разрешение контакта карта (slide + push-out)

```
function resolveKartVsStatic(kartOBB, pos, vel, colliders):
  for iter in 0..MAX_ITERS(=4):                  // мультиконтакт: угол/клин
    moved = false
    for col in nearby(colliders, pos):           // broadphase: клетки след±1
      mtv = satPolyPoly(kartOBB.at(pos), col.poly)
      if mtv == null: continue
      pos += mtv.n * (mtv.depth + SKIN)           // выталкивание по минимальной оси
      vn = dot(vel, mtv.n)
      if vn < 0: vel -= mtv.n * vn                // гасим ТОЛЬКО входящую нормаль → I2 slide
      moved = true
      kartOBB = rebuild(pos)                       // OBB сдвинулся, пересобрать
    if not moved: break
  return { pos, vel }
```

- **I2:** `vel -= n·(v·n)` при `v·n<0` — тангенциальная компонента живёт → скольжение.
  Никакого restitution для стен (аркада, без пинбола). Это та же схема, что уже в
  `resolveKartPush` (v·n<0 guard) — консистентно, энергия не добавляется.
- **Push-out** позиционный, по MTV минимальной глубины.

### 3.3 Terrain step-up тоже должен скользить

Крутая грань плато / terrain-подъём >MAX_STEP и **край карты** (`sample==null` за
границей) остаются в heightfield-логике — но их РЕАКЦИЯ меняется с «обнулить ось» на
«скользить». Реализация: если след упирается в rise>MAX_STEP или off-map, строим
нормаль стены `n` = направление против градиента высоты (для off-map — от ближайшей
границы клетки) и прогоняем ту же slide-формулу, что в 3.2. Так terrain-стены и
shape-стены разрешаются одним примитивом.

`wall_block*` перестаёт быть «heightfield null» для целей блокировки — его блокирует
shape-система (AABB). Heightfield всё ещё возвращает `null` под wall-клеткой (нет
walkable-высоты), но OBB карта туда не пускает, так что vertical.ts не читает null
под центром (см. §4 про фолбэк, если центр всё же над null).

### 3.4 Порядок резолюции в substep

```
step(dt):
  1. bicycle.step → vel, yaw                      # физика тюнинга, не трогаем
  2. pos += vel*dt                                 # кандидат XZ (можно axis-split как сейчас)
  3. resolveKartVsStatic(...)                      # стены+пропсы: SAT slide + push-out (3.2)
  4. resolveKartPush(kart-vs-kart круги)           # как сейчас, потом ре-валидация:
        re-resolveKartVsStatic (толчок не должен пропихнуть в стену)
  5. groundY = multiPointGround(...)               # §4, I3
     stepVertical(groundHeight=groundY)            # launch/gravity как есть
  6. attitude (pitch/roll) из ТЕХ ЖЕ проб          # §4
```

### 3.5 Стабильность на 120 Гц

- **Туннелирование:** 0.204 м/substep (maxSpeed 24.5 / 120). Мин. зазор форм ~0.9 м
  (пропсы) / 1 м (стены) ≫ 0.204 → туннеля нет. Тонкие (<0.4 м) стены в будущем →
  риск, митигация свипом (см. §7). Сейчас не нужно.
- **Джиттер (`.claude/rules/smooth-values.md`):** push-out непрерывен по глубине;
  нормаль контакта у выпуклого тела при шаге <0.2 м меняется плавно. В тесном клине
  два коллайдера могут толкать встречно — ограничиваем `MAX_ITERS=4` + MTV-минимум,
  остаточный дрожь < skin. Скорость: только `v·n<0` → энергия не растёт, без пинбола.
  Ни одного бинарного on/off порога в резолюции нет.

## 4. Высота корпуса на склонах (I3)

Одна `GroundProbe`-выборка на substep, переиспользуемая высотой и наклоном:

```
function sampleGroundProbes(map, pos, fwd, right, halfWB, halfTrack):
  center = map.sample(pos)
  hF = map.sample(pos + fwd*halfWB);  hB = map.sample(pos - fwd*halfWB)
  hR = map.sample(pos + right*halfTrack); hL = map.sample(pos - right*halfTrack)
  return { center, hF, hB, hR, hL }
```

- **Высота привязки (I3):** `groundHeight = max(всех НЕ-null проб)`.
  - V-жёлоб (вогнутый): центр читает дно, углы — склоны → `max` поднимает корпус,
    он «мостит» два склона, не тонет.
  - Перелом-гребень (выпуклый): `max` = передняя кромка → корпус стоит на гребне,
    корма/нос могут висеть → корректно, дальше launch.
  - Корма под картой на переломе: `max` + attitude-pitch держат корму.
  - Эта `max`-высота идёт в `stepVertical` вместо центральной точки.
- **null-пробы игнорируем** в `max` (кроме случая, когда ВСЕ null → тогда как сейчас
  fail-safe в freefall). Это чинит и краевой баг: центр над null-клеткой (узкий
  зазор меж диагональных стен) больше не роняет карт, если углы на земле.
- **Наклон (attitude):** `pitch = atan2(hF-hB, 2·halfWB)`, `roll = atan2(hR-hL,
  2·halfTrack)` — как сейчас в `attitude.ts`, но из ОБЩЕЙ выборки (без второго сета
  семплов).

### 4.1 Дружба с launch / gravity / trampoline

`vertical.ts` остаётся авторитетом по airborne/баллистике. Меняется ТОЛЬКО вход
`groundHeight`: центр → `max`. Проверка на регрессию launch:

- Гладкая рампа: все пробы растут синхронно, `max` растёт со скоростью склона →
  `groundRateNow` = vy → launch НЕ срабатывает (инвариант «плавный подъём не
  запускает»). Сохранено.
- Верх рампы выполаживается: `max` держит высоту на тик дольше (передняя проба) →
  launch чуть позже, корпус чище сходит с гребня. Приемлемо/лучше.
- **Риск:** launch-детектор чувствителен к rate. Если `max`-скачок на стыке клеток
  даст ложный launch — **развязать**: rate для launch считать по ЦЕНТРУ (как сейчас),
  а высоту привязки брать `max`. Это дешёвая страховка, решается на этапе тюнинга
  (Phase 3), тест `vertical.test.ts` с числами arena_slice — гейт.

## 5. Источник контуров из GLB (§ бюджет: load < 1 c, память копейки)

| Форма | Как получаем | Когда |
|---|---|---|
| wall_block* AABB | хардкод 1×1 (процедурные, размер известен) | — |
| structural OBB | `Box3.setFromObject(template)` (уже есть в `placeProp`) × `def.rot` | на размещении |
| natural hull | **XZ convex hull вершин меша**, monotone chain, симплификация ≤8 верт | бейк 1 раз на тип ассета |

- **Бейк hull:** пройти `geometry.attributes.position`, спроецировать в XZ, Andrew's
  monotone chain → выпуклый полигон, упростить до ≤8 вершин. Один hull на УНИКАЛЬНЫЙ
  ассет (не инстанс). ~десяток ассетов × сотни вершин = sub-ms, память ~8 верт × N.
- **AABB→OBB достаточно?** Для боксовых structural — да. Для камней — нет (owner
  хочет тереться о реальный край), поэтому именно там hull. Компромисс верный: hull
  только где он оплачивает feel.
- **Бейк-на-загрузке vs прекомпьют-таблица:** клиент грузит GLB — может бейкать live.
  НО сервер GLB не грузит (§6) → нужна **committed JSON-таблица** форм. Решение:
  один инструмент `tools/bake-collision-shapes.mjs` генерит
  `public/collision-shapes.json` (asset → локальный XZ-полигон/бокс), коммитим.
  Клиент и сервер читают её. Клиент дополнительно может бейкать live и тест сверяет
  live-hull == committed (анти-дивергенция, §7).

## 6. Сервер (минимальный shared/)

Цель: сервер (ракеты сейчас, authoritative-карт потом) использует ТЕ ЖЕ формы. Сервер
на Node, без THREE/GLB — поэтому геометрия приходит из committed JSON.

Новое в `shared/` (pure, без THREE, импортируется и браузером, и Colyseus):

- `shared/collision2d.ts` — примитивы: `ConvexPoly/Obb/Aabb/Circle`, `satPolyPoly`,
  `pointInPoly`, `segmentVsPoly` (для ракет), `projectOntoAxis`. + тесты.
- `shared/collisionShapes.json` — бейкнутая таблица форм по имени ассета (§5).
- `shared/staticColliders.ts` — `buildStaticColliders(MapJson, shapesTable) →
  ConvexPoly[]`. Тот же вход `MapJson`, что у `Heightfield.fromMapJson`. Pure.

Использование:
- Клиент: `kart.ts` резолвит OBB карта против `buildStaticColliders(...)`.
- Сервер: ракеты — `segmentVsPoly` против того же набора (сейчас только terrain);
  будущий authoritative kart — `resolveKartVsStatic` тем же кодом.

Это минимум: одна JSON + один builder-модуль. Вся SAT-математика уже pure и шарится.

## 7. Без внешнего физдвижка — обоснование

Наша задача: 2D выпуклый SAT + heightfield. Это ~300 строк pure TS, тестируемо,
детерминированно.

| Критерий | Custom 2D | rapier3d / cannon |
|---|---|---|
| Bundle | <15 KB кода | rapier ~1–3 MB wasm / cannon большой JS |
| Детерминизм (будущий authoritative сервер) | одна pure-TS математика клиент+сервер, бит-в-бит | wasm/JS float-расхождения, гемор для lockstep |
| Интеграция с bicycle-моделью | shape-резолв поверх нашей vel, физика тюнинга нетронута | 3D rigidbody-solver будет драться с bicycle |
| 2.5D природа | ровно наш случай | тянем 3D-стекинг/джоинты, которые не нужны |

**Вердикт: custom.** Rapier оправдан только если понадобится полноценная 3D-физика
(стеки ящиков, суставы, тряпичные куклы) — не наш кейс. Для 2.5D аркады кастомные 2D
формы + heightfield достаточно, и выигрыш по детерминизму для будущего сервера решает.

## 9. План миграции (поэтапно, без большого бэнга)

**Phase 0 — Скаффолд (нулевое изменение поведения).**
`shared/collision2d.ts` + тесты; `tools/bake-collision-shapes.mjs` →
`collisionShapes.json`; `shared/staticColliders.ts` + тесты. Не подключено к карту.
*Объём: средний (новые pure-модули, хорошо тестируемы), ~1 фокус-сессия.*
*Регресс-гейт:* юнит-тесты SAT (box-box overlap/MTV, hull-point, segment-poly).

**Phase 1 — Стены скользят (замена axis-kill для wall_block).**
Ввести OBB карта; в `kart.ts` step 8 заменить wall-null обработку на SAT-резолв против
wall-AABB; off-map + terrain step-up → slide вместо обнуления оси.
*Объём: малый-средний.*
*Регресс:* `footprintWall.test` (terrain step-up сохранён) + НОВЫЕ: «грэйз вдоль
стены сохраняет тангенциальную скорость», «сквозь стену не проходит», прогон против
`map_v2.json` (угловой лабиринт — не застревать). Плейтест «впритирку к стене».

**Phase 2 — Пропсы как формы (убрать дутые круги).**
Заменить круги пропсов на OBB(structural)/hull(decor) в `staticColliders`; резолв
OBB-карта SAT. Снять blend `(0.9+propR)/2` и shrink 0.8.
*Объём: малый-средний.*
*Регресс:* «сквозь камень не проехать», КЛЮЧЕВОЙ тест «позиция, которую блокировал
круг, теперь проходима вдоль реального края hull». kart-vs-kart круг не затронут.

**Phase 3 — Многоточечная высота (I3).**
`groundProbe.ts`; `attitude.ts` + `vertical.ts` на общий набор; `max`-высота в
`stepVertical`.
*Объём: малый; риск — ретюн launch feel.*
*Регресс:* `vertical.test` (числа launch arena_slice — ГЕЙТ), НОВЫЕ: «V-жёлоб —
корпус не тонет», «корма не проваливается на переломе». Если launch-регресс —
развязать rate(центр)/height(max).

**Phase 4 — Формы на сервере.**
Сервер грузит `collisionShapes.json` + `staticColliders`; ракета-vs-пропс. Задел под
authoritative-карт.
*Объём: малый.*
*Регресс:* ракета взрывается о пропс; тест «клиент-live-hull == committed JSON».

Порядок P1→P2→P3 независим по feel: каждую фазу можно шипнуть и плейтестить отдельно.

## 10. Риски

| Риск | Митигация |
|---|---|
| Снаг острого угла OBB карта о угол стены | skin ~0.02 + `MAX_ITERS`; фолбэк — capsule (стадион) для карта, если снаг виден в плейтесте |
| Регресс launch feel от `max`-высоты (P3) | развязать: launch-rate по центру, height по max; гейт `vertical.test` числами arena_slice |
| Джиттер в тесном клине (map_v2 угловой лабиринт) | `MAX_ITERS=4` + MTV-минимум; прогон-тест против map_v2.json |
| Бейкнутые формы расходятся с GLB при смене арта | `bake-collision-shapes.mjs` в asset-pipeline; тест live-hull(клиент) == committed JSON |
| Дивергенция клиент/сервер по формам | единый `staticColliders.ts` + одна JSON = единственный источник |
| Тонкие будущие стены (<0.4 м) — туннель на maxSpeed | сейчас не актуально (мин. зазор 0.9 м); при появлении — свип-тест (сегмент центра vs поли) |
| Две формы карта (OBB статика / круг 0.9 карт) путают | задокументировать; сознательный компромисс (карт-карт мягкий тюненый бамп) |

## 11. Открытые вопросы (для владельца / game-designer)

1. **Карт-форма: OBB или капсула?** OBB = точная флеш-парковка к плоской стене
   (буквальный запрос «впритирку»), но острый угол может цепляться о угол стены.
   Капсула глаже на углах, но оставляет зазор радиуса у плоской стены. Рекомендую
   стартовать с OBB + skin, капсула — фолбэк по плейтесту.
2. **Skin/зазор пропсов.** Тереться о буквальный hull (skin ~0.02) или оставить
   маленькую аркадную «грацию» (skin ~0.05–0.1), чтобы шершавый край камня не давал
   резкий стоп? Влияет на ощущение «на грани».
3. **Merge wall-клеток** в крупные AABB на билде — делаем сразу (меньше форм) или
   позже как оптимизацию? Для текущих карт число стен невелико, можно отложить.
4. **Authoritative-карт на сервере** — в скоупе сейчас (тогда Phase 4 полнее) или
   только ракеты, а карт остаётся client-local? От этого зависит, насколько строго
   держать бит-в-бит детерминизм резолва.
